# .claude-memory/

Per-machine, per-workspace Claude Code auto-memory pools. **Git-synced
across machines** so a memory written in any session lands here and
flows to every other machine you run OPS on. This is one of the
load-bearing ideas in OPS: durable knowledge lives in tracked files on
disk, not in a context window that dies on compaction.

## How it's wired

Claude Code writes auto-memory to
`~/.claude/projects/<encoded-cwd>/memory/`, where `<encoded-cwd>` is the
working directory with every `/` replaced by `-` (e.g., `~/OPS` →
`-home-operator-OPS`, a root session → `-root`). Left alone, that memory
would sit under `~/.claude/`, untracked and stranded on one machine.

`.claude-config/bin/memory-init` walks every encoded subdir Claude Code
has created under `~/.claude/projects/`, moves each `memory/` dir into a
git-tracked pool, and symlinks the original path to it:

```
~/.claude/projects/<encoded-cwd>/memory/
    → symlink → ~/OPS/.claude-memory/<hostname>-<encoded-cwd>/
```

Everything Claude writes to memory now lands directly in this
git-tracked directory. `memory-init` is idempotent: safe to re-run
on a machine that's already set up.

The `<hostname>-` prefix keeps machines separate when the same workspace
is used on more than one host, so `laptop-...` and `workstation-...`
pools never collide even though both encode the same `~/OPS` cwd.

Stage 2 (`.claude-config/deploy.{sh,ps1}`) runs
`memory-init --auto-commit` during deploy, so a new machine wires
this automatically and commits its new pool. It pushes the commit only
when origin is verified private (`DEPLOYMENT.md`, "The push gate");
otherwise the commit stays local and the deploy output says why.

**Second profile.** If you run a second Claude Code profile via
`CLAUDE_CONFIG_DIR`, `memory-init` points that profile's per-cwd
memory symlinks at the SAME shared pool here: auto-memory is identical
across profiles rather than forked.

## What's inside each pool

Auto-memory entries follow the format documented in the user-level
`CLAUDE.md` (auto-memory section). Each entry is a single `.md` file
with frontmatter:

```markdown
---
name: <short-kebab-case-slug>
description: <one-line summary>
metadata:
  type: <user | feedback | project | reference>
---

<memory body>
```

Each pool also holds a `MEMORY.md` index: one line per memory file.
`MEMORY.md` is regenerated by `.claude-config/bin/memory-index` (through the
`memory-index.sh` SessionStart hook), never by hand. How a session reads the
pool depends on your auto-memory setting (below); the individual entry files
are read on demand when their `description` matches the work at hand.

## Housekeeping tools

- **`.claude-config/bin/memory-init`** (`memory-init.ps1` on Windows):
  initialize (or re-sync) all of this machine's memory pools. Run once per
  machine; the deployer runs it for you.
- **`.claude-config/bin/memory-index`**: regenerate a pool's `MEMORY.md`
  index after entries are added or removed. Its read-only modes print the
  session digest (`--digest`), the prompt hint (`--hint`), and a search by
  hand (`--find <words>`); `.claude-config/bin/README.md` has the details. A
  pool over 60 entries draws a warning and nothing else.
- **`memory-prune` skill**: the periodic audit. It inventories the pools
  (read-only), fans a classification pass over every entry, and returns a
  keep / promote / move / discard action table, then executes it after you
  sign off; deletes stay operator-gated. (The fleet-era `ac-memory-gc`
  inventory and its weekly `ops-memory-gc` timer are retired.)

## What goes here vs `CONTEXT/`

- `.claude-memory/`: durable Claude-written context built up by AI
  sessions over time. Auto-managed; sessions add, update, and (with
  approval) remove entries as they learn.
- `CONTEXT/`: Operator-authored identity + doctrine files. Edited by
  the Operator (or by an AI with the Operator's approval), not
  auto-managed.

A memory entry that has hardened into durable identity or doctrine
should be promoted OUT of here and INTO `CONTEXT/`: the `memory-prune`
skill surfaces those promotion candidates.

## How a session loads its pool

Your auto-memory setting picks the loader; OPS follows it and never changes it.

- **Native auto-memory on.** Claude Code loads the current workspace's
  `MEMORY.md` at a fresh session and after a compaction, and writes new
  entries itself.
- **Native auto-memory off** (`autoMemoryEnabled: false`, which the current
  Stage-1 settings set). Claude Code neither loads nor writes memory. The
  `memory-digest.sh` SessionStart hook prints a digest of this directory's
  pool and the OPS root pool's cross-project entries on every start, resume,
  clear, and compact: at most 9,000 characters, pinned entries first, then
  user and feedback entries, then the rest, with names only past the budget.
  A session writes an entry by hand in the format above, then runs
  `memory-index <pool dir>`; the digest's Write line says the same.
  `MEMORY_DIGEST=1` or `0` forces the hook on or off.

Either way, `memory-hint.sh` adds up to three relevant entries to a prompt
that strongly matches them. Sessions don't need to `Read` this folder; the
only reason to look here directly is to debug memory drift or hand-edit an
outdated entry.

## Git note

This directory is intentionally NOT gitignored, even though it sits next
to `~/.claude/` machinery. Tracking it across machines is the feature:
don't fold it into `.gitignore`.
